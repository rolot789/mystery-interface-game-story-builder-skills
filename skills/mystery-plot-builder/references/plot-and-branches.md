# 사건·분기 설계

## 진상과 기록

Fact는 참인 명제다. 거짓말이나 오해는 Claim에 둔다. 사건 당시의 실제 시각과 기록 시각을 분리한다. 시점이 미정이면 null이나 기간·상대 순서로 표현한다. 정밀한 시각을 임의로 꾸며 Canon으로 만들지 않는다.

Trace는 사건·일상·시스템 활동의 기록 개요다. 주요 증거 기록에는 원인 Event, 작성자 또는 시스템, 작성 시점, 남은 내용, 왜곡, 접근 방법을 연결한다. supports / contradicts 링크에는 추론 이유와 대안 해석을 설명한다. 같은 원본을 전재한 두 문서는 독립 근거로 세지 않는다.

## 시간과 장소

시각은 TimeSpec으로 적는다.

- **정확한 시각.** 기록에 찍히는 시각처럼 정확해야 하는 것은 시간대 오프셋이 있는 ISO 시각으로 적는다.
- **불확실 구간.** `{earliest, latest, label}`로 적는다. "그 주 초", "자정 무렵 어느 때"처럼 범위만 아는 경우다.
- **미정.** null로 두고, 순서만 preconditions로 표현한다.

사건은 location_id와 duration_minutes를 가질 수 있다. 같은 인물이 등장하는 사건들은 장소와 시각이 서로 양립해야 한다. 이동에 걸리는 시간은 World Builder가 Location.connections에 정한 값을 쓰고, 사건마다 새로 정하지 않는다. 한 장소가 다른 장소 안에 있으면(방과 건물) 동시에 있어도 모순이 아니다.

배경 역사(HistoryEvent)는 World Builder가 소유한다. 사건이 과거의 제도 변화나 사고에 기대면 preconditions에 그 HistoryEvent를 넣는다. 사건의 인과 사슬에 직접 들어가는 과거 행동이면 HistoryEvent가 아니라 Event로 만든다.

## 기록과 서비스

게임에 나오는 기록은 대부분 어떤 서비스가 남긴 것이다. 기록마다 다음을 정한다.

| 필드 | 정할 것 |
|---|---|
| service_id | 기록을 저장한 Service |
| artifact_type | 그 서비스가 선언한 기록 유형(메시지, 메일, 문서 버전 등) |
| created_at | 기록이 생긴 시각. 원인 사건보다 앞설 수 없다 |
| author_id | 실제 작성자. 대필·사칭이면 표면상 발신자는 distortion에 적는다 |
| state_at_present | 조사 현재 시점의 상태: PRESENT(남음) / DELETED(삭제됨) / ALTERED(조작됨) |
| retention_exception | 보존 기간이 지났는데도 남아 있다면 그 이유(백업, 법적 보존, 버그) |

기록의 보존 기간, 삭제 흔적, 수정 표시, 접근 권한은 World Builder가 Service에 정한 규칙을 따른다. 플롯에 필요하다고 서비스 규칙과 다르게 동작하는 기록을 만들지 않는다. 규칙을 바꿔야 하면 World Builder에 변경을 요청하고 파급을 검토한다.

지워진 기록도 설계 대상이다. DELETED 기록은 플레이어가 볼 수 없지만, 삭제 흔적("삭제된 메시지"), 알림 미리보기, 상대 기기의 사본처럼 서비스 규칙이 남기는 흔적은 별도의 Trace로 만들 수 있다.

## 허점

사건이 세계 규칙의 빈틈을 이용했다면 Event에서 WorldRule이나 Service로 exploits 링크를 만든다. reason에는 이 사건에서 그 허점이 어떻게 쓰였는지 적는다.

- 허점이 왜 존재하고 왜 아직 막히지 않았는지는 World Builder가 incident-interface 기준으로 정한다.
- HARD 규칙을 이용했다면 규칙을 깨뜨린 것이 아니라 규칙의 적용 범위 밖을 이용한 것이어야 한다. 그 범위를 규칙의 exceptions에 적도록 요청한다(WORLD-004).

## 공정성

플레이어가 해답에 도달하는 데 필요한 것은 해답 전에 볼 수 있어야 한다. 해금 그래프 전체는 후속 범위지만, 다음 표는 기획 단계에서 만든다.

| 해답에 필요한 것 | 드러내는 기록 | 플레이어가 찾는 경로 | 해답 전에 볼 수 있나 |
|---|---|---|---|
| 핵심 Fact | supports 링크가 있는 Trace | 접근 방법(access) | 예 / 아니오 |
| 이용된 규칙·허점 | 규칙을 origin_ids로 갖거나 링크로 연결된 Trace | 공지, 약관, 동료의 말 등 | 예 / 아니오 |

- **숨은 규칙.** SECRET·INSIDER 규칙이 해답에 쓰이면 연결된 Trace가 하나 이상 있어야 한다(FAIR-001).
- **레드 헤링.** 잘못된 방향으로 이끄는 기록도 세계 안에서 생길 이유가 있어야 한다. origin_type이 routine이나 system인 기록, 또는 다른 인물의 실제 행동에서 나온 기록으로 만든다. 플레이어를 속이려고만 존재하는 기록은 만들지 않는다.
- **마지막 문서 금지.** 해답이 마지막에 발견되는 문서 한 장의 고백에만 기대지 않는다. 핵심 Fact마다 서로 독립인 근거를 둘 이상 둔다.

## 분기

initial_state는 불리언·문자열·숫자 값의 사전이다. 선택은 available_when과 options를 갖고, 각 option은 condition과 effects를 갖는다. 효과는 이미 선언된 상태 변수의 값만 바꾼다. 과거 Fact를 효과로 덮어쓰지 않는다. 같은 Choice는 한 경로에서 한 번 실행한다. 반복 행동이 필요하면 분리된 선택으로 설계한다.

조건 문법은 true/false, {"all":[조건,...]}, {"any":[조건,...]}, {"not":조건}, {"var":"변수명","eq":값}이다. 비어 있는 all/any는 허용하지 않는다. 임의 코드나 eval을 사용하지 않는다.

Ending은 condition, consequences, witness를 갖는다. witness는 [{"choice_id":"선택 ID","option_id":"옵션 ID"}, ...]이다. 초기 상태에서 선택 조건과 효과를 순서대로 적용해 결말에 도달하는지 검증한다. witness는 가능한 한 경로의 증거이며 전체 경로의 완전한 분석을 뜻하지 않는다.

결말은 동시에 성립 가능한 결과 묶음이면 exclusive=false, 단일 결말이면 exclusive=true다. 단일 결말 조건이 같은 경로에서 겹치면 수정하거나 우선순위를 사용자와 명시해야 한다. 기본적으로 숨은 우선순위로 해결하지 않는다.

## 서사 점검

선택 결과는 완전히 예측 가능할 필요가 없으나 행동과 결과 사이에 설명 가능한 원인이 있어야 한다. 도덕적 정답을 하나로 강제하지 않는다. 플레이어가 얻는 정보와 진상 전체를 동일시하지 않는다. 완성 기획에서 각 결말의 인물·조직·공개 정보에 생기는 실질적 차이를 설명한다.
